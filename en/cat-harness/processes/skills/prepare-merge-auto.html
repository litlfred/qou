/prepare-merge-auto — Autonomous merge pipeline

Skill prepare-merge-auto: Full autonomous prepare-merge → resolve → merge pipeline. Coordinates with sibling PRs, resolves review comments, asks structured questions only when blocked, then merges.

Named by: Adopt a methodology from a source document, Translation Workflow, Copy a knowledge-graph asset into a folio, A sub-graph wants to leave, Authorise the extraction, Move the graph into its repositories, Prepare a graph to stand alone, A knowledge graph leaves for its own repositories, Build and publish a per-slice SQLite file, A sub-KG is staged in place, then leaves for its own repository, Ask the person, CRDM close-out, CRDM data model, CRDM Phase 6 — implement, MVP, acceptance, CRDM — link the work to an issue, CRDM Phase 1 — needs, CRDM Phases 2–4 — BPA and requirements, CRDM requirements, CRDM Phase 5 — beans and sign-off, Hand back to the discussion, Related work: find, sort, summarize, ask to coordinate, Secure agent permissions, Session state machine, Wireframe design review, Contributor feedback on a working draft, Record agent step, Review-log watch

Runs the full /prepare-merge workflow PLUS:

  1. Sibling coordination (before starting)
  2. Review-comment resolution (after reviews land)
  3. Structured user questions (only when genuinely blocked)
  4. Merge (after all comments resolved, strictly through Process_MergeToMain / Process_MergeTrain)

1. Only the Active merge-steward Merges onto main

  • Siblings NEVER self-merge onto main when a merge-steward is active. Only the single session holding the merge-steward lane writes to main (under explicit owner release recorded per merge-to-main.md).
  • Sibling handoff contract (sibling-session lane): When a sibling finishes its branch and passes local verification (lean-direct-cone.sh -j 1 / lean-library-sweep.py, precision-gates.sh --changed, check-sidecars.sh, voice-leak-audit.ts, two-step witness SHA stamp, 0 dirtied qou-v0t8 contended audit witnesses), it:
    1. Opens a Ready PR (--base main, using --body-file / shell=False so backticks survive intact) with a linked GitHub issue (Closes #<issue>) and zero unticked - [ ] boxes;
    2. Applies the ready-to-merge label (when authorized by the owner per merge-queue.md §”Ask the user before submitting”) and posts a signed ready: <full head sha> comment on the PR;
    3. Sends the 6-line merge request (PR #<n> + URL, Closes #<issue> + bean IDs, branch + ready: <full head sha>, authored files touched, local gate verdicts, overlap / ordering constraints) to the active merge-steward, then monitors status (never fire-and-forget, and never churn unnecessary rebases while queued far back).

2. Overlap-Partitioned Merge Trains (>= 2 Ready PRs Queued, Process_MergeTrain)

When >= 2 Ready PRs are queued, the merge-steward MUST NOT rebase, sweep, and rebuild main $N$ separate times sequentially. Instead, execute Process_MergeTrain:

  1. Overlap Partition (merge-overlap): Run bun run cat merge:overlap (folio-assistant/cat-harness-tools/scripts/merge-overlap.ts) over the open Ready PRs to classify authored vs generated/additive paths and partition admissible PRs into mutually independent batches of 4–8 PRs on merge-train/<base>-<n> (broadcasting hold to pushing siblings before assembling/landing the train, and done when finished per merge-manager-watcher.md).
  2. Stack Members & Regenerate Shared Additive Regions ONCE: Merge each admitted member onto merge-train/<base>-<n> in priority/PR order (--no-regen), then reconcile and regenerate additive/generated regions once across the combined train:
    • computations/q0_anchor_manifest.json (additive union of producer entries, +0 removals),
    • folio/quantum-observable-universe/lean/QOU.lean (sorted module umbrella imports),
    • folio/schema/references.ts + folio/references/*.json (ORDER union + references.bib regeneration when bibliography entries were added),
    • folio/**/*.qa.json via python3 scripts/qa-sidecar-agent-union.py --against <pre-rebase-ref> --apply (mechanically preserving all agent verdicts whose field_hash still certifies the merged block).
  3. Run the Combined Gate Suite ONCE on merge-train/<base>-<n>:
    • python3 scripts/lean-library-sweep.py (plus bash scripts/lean-content-sweep.sh <changed content-block .lean> if any content sibling .lean changed — require VERDICT: GREEN, exit 0; exit 8 INCOMPLETE is NOT green),
    • bun run scripts/run-validate.ts folio/quantum-observable-universe (and bash scripts/check-sidecars.sh),
    • bun run folio/pipeline/voice-leak-audit.ts (L1–L4 clean on touched blocks),
    • python3 scripts/compute-qa.py --all --base origin/main (diff/ratchet gates clean; revert any dirtied qou-v0t8 tree-measuring audit witnesses via git checkout -- computations/audits/ computations/*.witness.json).
  4. Bisect & Eject ONLY Red Culprits (Process_MergeRefusal): If the combined train fails a gate, attribute (Task_Attribute) or bisect (Task_Bisect) to isolate ONLY the red culprit PR(s). Eject ONLY the culprit(s) — never abort the green members and never edit authored code inside the train — handing each culprit back via Process_MergeRefusal (Merge refused: #<n> <cause> blocking bean + in-place PR status comment), re-assemble the remaining green members on merge-train/<base>-<n>, and re-verify once.
  5. Land in Train Order & Verify Replay (Process_MergeToMain): Land each green member in train order under recorded owner authorisation (merge-to-main.md), NEVER passing --delete-branch (delete_branch_on_merge is strictly forbidden — preserve every local and remote branch), verify EVERY landed member with python3 scripts/verify-merge-replay.py --branch origin/<branch> --merged <merge-sha> (MISSING: 0), run post-merge-rebuild (bash scripts/publish-main-local.sh --deploy) once on the new main tip, and post done.

Workflow

Phase 0: Sibling coordination

Before starting the merge pipeline, identify sibling PRs whose scope overlaps this branch’s files:

mcp__github__list_pull_requests(owner, repo, state="open")

For each sibling PR that touches the same files or content domain:

  • Post a brief coordination comment: “Starting prepare-merge on #; touches . Review welcome if you'd like to check for conflicts before merge."
  • Do NOT wait for responses — this is a courtesy notification, not a blocking request.

Phase 1: /prepare-merge (steps 1–6)

Execute the full /prepare-merge skill (rebase, integrate, one-voice, Lean build, final rebase, request reviews). All steps must succeed before proceeding.

🛑 If the branch touches any .lean, the Lean step is a SWEEP, not bare lean-direct. /prepare-merge §4 carries the reasoning; the short version is that lean-direct against the restored olean cache verifies against a snapshot, so a library signature that moved afterwards leaves the file green and broken at once. That is not hypothetical — descartesWtrace recorded exit 0 and landed on main red (#6751).

# If rebasing a pre-Q3 branch that still places/imports modules under legacy `QOU/<OldSynonym>/`:
nice -n 10 python3 scripts/apply-lean-reservoir-migration.py --fixup-branch

scripts/lean-content-sweep.sh <changed content-block .lean ...>   # or no args
scripts/lean-library-sweep.py                                     # unified dirty closure across MathlibExt + 6 Tier-B libs + QOU

Both rebuild from source only the modules whose own olean predates their own last source commit, and never invoke lake, so the restored cache is not evicted. Library sweep is 122 s on a 74-module closure; the content sweep is ~50 min for all 261, so pass the changed files when you have them and SHADOW=<dir> to reuse the shadow.

Record which one ran, in the PR, in these words — this is the Phase-4 verification gate’s evidence and the distinction it turns on:

  • “lean-library-sweep.py: N/N dirty modules rebuilt from source, exit 0” — source-verified. Quote its VERDICT: line. Exit 8 (INCOMPLETE) means no RED but some module TIMEOUT / UNVERIFIED / BLOCKED: that is not a green, so do not write “exit 0” for it (bean qou-tpdg).
  • “lean-direct against the restored cache, exit 0” — snapshot-conditional. Say so, and say why the sweep was not run.

A sweep result is container-scoped (the dirty closure is computed against this container’s olean tree) and does not cover the UGB or Fred2005 packages. Do not write either limit out of the PR. Bean qou-56qy.

Sidecar conflicts during the rebase. Resolve content/**/*.qa.json to either side as usual for the script entries, then restore the other side’s agent entries mechanically:

python3 scripts/qa-sidecar-agent-union.py --against <pre-rebase-ref> --apply

An agent verdict has no producer — qa-sweep regenerates script candidates and never a judgement — so “let the pipeline re-run it” loses those entries silently. The #5103 takeover dropped 7381 of them that way (qou-tqr9). The script is additive and skips any entry whose field_hash.md no longer certifies the merged .md.

Wait protocol (15-minute window — extended 2026-05-31 per author):

  1. After requesting reviews in Phase 1, poll for Copilot’s check-run status every 30 seconds (up to 15 minutes): 
    mcp__github__pull_request_read(method="get_check_runs", ...)

    Look for the copilot-pull-request-reviewer check run:

    • "status": "queued" or "status": "in_progress" → reviewer has noticed the PR; keep polling every 30s
    • "status": "completed" → reviews are in, proceed immediately
    • No check run after 2 minutes → reviewer did not trigger for this file type (e.g. skill-only PRs with no code); proceed with 0 comments

  2. Check that Copilot reviewed the CURRENT head. A review whose commit_id is an earlier commit is stale and does not count — re-request with mcp__github__request_copilot_review and keep polling. (PR #4456 carried a 13-file review against an 85-file head.)

  3. 15-minute hard cap: if Copilot has not completed after 15 minutes, proceed with whatever comments have landed. Note “Copilot: timed out (15 min)” in the briefing.

Once reviews arrive (or the 15-minute cap is reached), give the user a concise status briefing:

  1. PR identity: “#N — title” with clickable URL
  2. Branch: branch-name → main
  3. Scope: files changed, additions/deletions, commits
  4. Review comments received: total count, by reviewer, with 1-line summary of each thread: ``` Review comments (3 total — Copilot: 3):
    1. [Copilot] line 42 engine.py — threshold mismatch
    2. [Copilot] line 98 engine.py — unused variable
    3. [Copilot] line 173 engine.py — spelling fix ```
  5. Disposition plan: for each comment, state the planned action (accept / modify / reject / escalate) BEFORE making changes — so the user can redirect: 
    Plan: accept 1,2,3; accept-with-modification 4; reject 5
(reason: "classical limit" is the standard term per §7a)
  6. CI status: green / failing / pending

The user can reply with overrides (e.g. “reject 4”, “skip 2,3”). If no override within ~30 seconds, proceed with the stated plan.

Phase 2: Resolve review comments

After the briefing (and any user overrides), triage each thread:

Classification Action
accept Apply the suggested fix, commit, push.
accept-with-modification Apply a modified version, commit with explanation.
reject-with-reason Reply on the thread with the reason (e.g. “intentional — see §X”).
escalate Cannot resolve autonomously — proceed to Phase 3.

For each resolved thread, commit the fix with message: fix(PR #N): address <reviewer> thread r<id> — <1-line summary>

Push after each batch of resolutions.

Phase 3: Structured user questions (only when blocked)

If any review comment requires a judgment call (ambiguous intent, architectural decision, multiple valid approaches), use AskUserQuestion with:

  • Rich context per AGENTS.md user-accessibility rules:
    • Quote the exact comment + file path + line number
    • Show the current code vs proposed change (preview)
    • State trade-offs for each option
    • Default to multiSelect: true unless choices are mutually exclusive
    • Prefix with 🟡
  • Batch questions — collect ALL blocked items into a single AskUserQuestion call (up to 4 questions) rather than asking one at a time.

Phase 4: Merge (Process_MergeToMain — Active merge-steward Only)

Reminder: Only the active merge-steward executes Phase 4 (or runs it across 4–8 PRs simultaneously via Process_MergeTrain when >= 2 Ready PRs are queued). A sibling session stops after Phase 2/3, applies ready-to-merge + signed ready: <full head sha>, and sends the 6-line merge request to the merge-steward.

After all review comments are resolved (or the user has answered all escalated questions):

  1. Run bun run scripts/run-validate.ts folio/<paper> (and bun run folio/pipeline/voice-leak-audit.ts if folio/ prose changed) one final time.
  2. If the branch touches any .lean, the sweep from Phase 1 must have run on the FINAL head, and its result must be in the PR. A sweep on an earlier commit is not evidence about what is being merged — the final rebase in /prepare-merge §5 moves the branch onto a main whose library may have shifted underneath it, which is the exact mechanism this gate exists for. Re-run it after that rebase, not before.
  3. Check CI status via mcp__github__pull_request_read get_check_runs. Expect total_count: 0 — auto-triggers are disabled repo-wide, so this returns nothing and is not a gate. Never read it as green.
  4. If all green: merge via mcp__github__merge_pull_request with merge_method: "rebase" (default per AGENTS.md §”Branch + PR workflow” rule 8 — replays the structured commits onto main linearly, no merge commit). Rule 8 is authoritative.
  5. CRITICAL: DO NOT DELETE THE BRANCH EVER! If using the GitHub CLI, DO NOT pass --delete-branch. If using the GitHub API, ensure the branch is preserved.
  6. Report the merge SHA + URL.

Phase 5: Post-merge verification, then coordination

Verify the merge replayed every commit — this phase had no check at all until 2026-09-04, and the failure it misses is on the record.

scripts/verify-merge-replay.py --branch origin/<branch> --merged <merge-sha>

A rebase-merge can land 7 of 8 commits and still report success through the API. PR #5111 did exactly that; it was recovered as #5125, and only because someone grepped main for the edited content.

Do NOT verify with git diff origin/main <merged-head>. After a rebase-merge the PR’s head becomes main’s tip, so that command compares a commit to itself and returns empty whether or not anything was dropped — strongest-looking evidence, zero information. Whenever the PR is the last thing merged (the normal case for this pipeline) it cannot fail. Ten PRs were merged on 2026-08-15 under an instruction calling it “the strongest check”; bean qou-vtau. Its mirror image misleads too: diffing main against the pre-merge branch head shows every sibling PR that landed in between as though it were yours.

The script compares patch-ids — a hash of each commit’s diff, invariant under rebase, where shas are not. Run --selftest if you want to confirm it can still detect a drop; it synthesises one and asserts the patch-id check catches what git diff misses.

Two behaviours to read correctly rather than “fix”:

  • a commit with an empty diff has no patch-id and is reported separately, not counted as replayed;
  • a commit whose content changed during the rebase (a conflict resolved differently) reports MISSING by design — it did not replay, and the resolution deserves a look.

Then coordinate:

  • Post a brief update on any sibling PRs that were notified in Phase 0: “PR # merged; updated on main. Please rebase if needed."
  • Unsubscribe from the merged PR’s activity.

Then rebuild the published site (owner, 2026-11-23). GitHub Actions is dispatch-only here, so nothing rebuilds the site on a merge. After every merge to main, follow post-merge-rebuild: check out the merged main and run bash scripts/publish-main-local.sh --deploy. If it cannot run (no platform checkout, a failed build), say so in the merge report; do not skip it silently.

Error handling

  • If /prepare-merge fails at any step, STOP and report the blocker. Do not request reviews on a broken branch.
  • If CI fails after pushing review fixes, investigate and fix before merging.
  • If the user doesn’t respond to Phase 3 questions within the session, leave the PR open with a summary comment listing the unresolved items.

Anti-patterns

  • Do NOT merge without resolving review comments (even if CI is green).
  • Do NOT squash unless the user explicitly says “squash” on this PR.
  • Do NOT wait on a Gemini review — Gemini Code Assist is sunset.
  • Do NOT block on a Copilot review — but do NOT skip reading it either. The “n=5, never enqueues” line that stood here is refuted; see the Phase 1b correction above. Reviews arrive (minutes), carry real findings, and are rationed — so request once, keep working, and read get_reviews before you merge. Never poll get_check_runs: it returns total_count: 0 whether or not a review exists, so it cannot tell you.
  • Do NOT verify a merge with git diff origin/main <merged-head> — after a rebase-merge that compares a commit to itself and can never fail. Run scripts/verify-merge-replay.py instead (Phase 5).
  • Do NOT skip sibling coordination — it prevents post-merge conflicts.
  • Do NOT ask trivial questions in Phase 3 — only genuinely ambiguous decisions warrant user input.
  • Do NOT delete the branch after merging.
  • Do NOT resolve a .qa.json conflict to one side and rely on qa-sweep to regenerate it — that is correct for script entries and drops agent verdicts (see Phase 1).
