Overview

This skill manages the library/ directory as an intake pipeline for converting raw documents into structured content objects. It handles:

  1. Scanned PDFs / images — OCR extraction → text → blocks
  2. LaTeX source — environment extraction → blocks
  3. WHO L1 → L2 guidelines — normative structure → blocks
  4. arXiv papers — fetched source → blocks (delegates to paper-importer)
  5. Arbitrary documents — best-effort structural analysis

The key distinction from paper-importer: this skill owns the full lifecycle of library/, including tracking processing state, partial extractions, and multi-pass refinement. Paper-importer focuses on the final content-object generation step.

When to Use This Skill

  • User says “upload”, “scan”, “process document”, “intake”
  • User drops a file into library/
  • User mentions WHO, L1, L2, guideline, normative
  • User wants to convert a raw document into content objects
  • Files appear in library/ that haven’t been processed yet

Pipeline Stages

Stage 1: Upload (→ uploaded)

Place raw files in library/<document-id>/. Create intake.json with source metadata. Files are committed to git for reproducibility.

Supported formats:

  • PDF — academic papers, scanned guidelines, reports
  • LaTeX — .tex source bundles
  • HTML — web-published guidelines, standards
  • DOCX — Word documents (WHO often distributes as Word)
  • Images — scanned pages (PNG, JPG, TIFF)

For academic papers, prefer the MCP fetch path (added 2026-05-22): when the session network allows the upstream host, use paper-search-mcp (arxiv / PubMed / bioRxiv / medRxiv) or openalex-paper-search (alex-mcp; OpenAlex catalog) rather than curl/WebFetch. The MCP tools return canonical metadata and the PDF in one call, eliminating the OCR-then-extract-then-name dance. See paper-importer.md §Phase 1 for the per-tool routing table. Sandboxed Claude-Code-on-the-web sessions (github-only allowlist) cannot reach those hosts; in those sessions, queue the fetch onto a normal-network machine per bib-qa.md §Batch intake pipeline.

Four things that matter here and are not guessable from the table:

  • The exit code is the diagnosis. pdf-extract.py returns 0 text · 2 no text layer, i.e. a scan · 3 a parser problem on a file that does have text · 4 bad usage. So “swap libraries” and “you need OCR” are decided by evidence rather than by trying things.
  • pdf-structure.py READS the OCR cache; it never runs OCR. On a scan the order is pdf-ocr.py first, pdf-structure.py --ocr second. The other way round the sections come out empty.
  • An OCR’d document whose structure was never re-run is invisible to a sections/ grep — which is corpus-grep path 5. Measured here: 26 library/*/ocr/ trees against only 11 structure.json recording "text_source": "ocr", so ~15 documents have their text on disk and a stub in sections/. library/procrsoclondona92/ is the worked case: 1,916 bytes of JSTOR download banner in sections/ against 46,511 bytes of real text in ocr/. This is the same “fourth tier” AGENTS.md describes — and the producer it could not name is pdf-ocr.py, whose output path is literally page-{i:03d}.txt.
  • The OCR and table backends are NOT in the shipped image. Measured 2026-09-16: grep -ci tesseract Dockerfile → 0, pdfplumber → 0. So pdf-ocr.py refuses with an install hint and pdf-tables.py writes status: "n/a-no-backend" there. Check before assuming, with python3 folio-assistant/scripts/pdf-ocr.py --check and python3 folio-assistant/scripts/pdf-tables.py --check; a n/a is the contract working, not a failure to diagnose.

Output: extracted-text.md — raw markdown with preserved structure.

Stage 3: Structural & Claim Analysis (→ structured)

Analyze extracted text for formal environments, scientific claims, and document structure:

For academic papers (Math + Deductive Logic vs Science + Empirical Evidence):

Stage-B extraction (folio-assistant/cat-harness-tools/scripts/extract-candidates.py, loading folio-assistant-sci/scripts/extractors/math-environments.py scoped to qou’s needs closure) populates library/<doc-id>/candidates.json (ingest-candidates/v1) and typed blocks/*.jsonld nodes. It explicitly differentiates:

  1. Math Claim + Deductive Logic (claim_domain: "math"):
    • Multi-line formal declarations (Theorem, Proposition, Lemma, Corollary, Definition, Conjecture, Claim, Axiom, Postulate, Property, Fact, Criterion, Hypothesis, Remark, Example), supporting both Theorem 2.1. and Bourbaki 2.1. Theorem. headers and filtering out prose cross-references ("Theorem 2.1 has...").
    • evidence_kind: "deductive-proof", "axiomatic-definition", "conjectural", or "explanatory".
    • route_to: "formalizer" for formalizable mathematical claims.
  2. Science Claim + Empirical / Computational / Analytic Evidence (claim_domain: "science"):
    • Extracted from physics, lattice-QCD, phenomenological, and experimental papers where load-bearing results are stated outside Theorem N blocks.
    • evidence_kind:
      • "empirical-measurement" (experimental observations, detector measurements, physical values with uncertainties ±, (stat)(syst), σ, % C.L.) -> route_to: "compute-check".
      • "computational-simulation" (lattice QCD+QED, Monte Carlo, ab initio numerical determinations) -> route_to: "compute-check".
      • "analytic-derivation" (theoretical physics derivations, dispersion relations such as Cottingham’s formula, Compton sum rules, effective Lagrangians) -> route_to: "formalizer" (or "compute-check" when numerical).
    • Rule: Empirical and numerical claims (route_to: "compute-check") are cross-checked against computation witnesses and comparison paragraphs, never wired into formal Lean theorems as axioms.
  3. Evidence Location Provenance (evidence_location: "in-paper" | "elsewhere" | "both" | "none"):
    • "in-paper": proved, derived, computed, or measured in this document (captures proof_excerpt from following Proof. blocks, deferred proof pointers "proved in Section 4", or in-paper measurements/simulations).
    • "elsewhere": attributed to an external paper or dataset (Theorem 2.2 (Rumer, Teller, Weyl), Proof. See [14, Thm. 3.1]., "A previous publication [4] gave the values..."), with citations listed in external_refs.
    • "both": combines an external theorem/measurement with an in-paper proof or calculation.
    • "none": stated without proof ("proof omitted / routine") or an open conjecture.

For WHO guidelines (L1 → L2):

WHO guidelines have a specific normative structure:

WHO element Content block kind Notes
Recommendation (numbered, boxed) definition Normative statement
Evidence summary prose Supporting narrative
Remarks remark Implementation notes
Good practice statement proposition Consensus-based
Research priority conjecture Open questions
Background prose Context sections
GRADE table diagram Evidence quality

L1 vs L2:

  • L1 = Recommendation (what to do) — maps to definition blocks
  • L2 = Implementation guidance (how to do it) — maps to prose blocks tagged ["implementation", "L2"]

The structural analysis identifies these elements and maps them to the content-object type system.

Output: extracted-blocks.json — array of detected blocks with provisional kinds, titles, and content.

Stage 4: Mapping (→ mapped)

Interactive step — present extracted blocks to user for review:

  1. Show block count by kind
  2. Let user rename, reclassify, skip, or merge blocks
  3. Let user define chapter/section structure
  4. Let user set the target paper ID
  5. Generate mapping.json with confirmed decisions

Stage 5: Content Generation (→ generated)

Generate content objects under content/<paper-id>/:

  1. .ts manifests via folio/schema/builders.ts
  2. .md content in project markdown conventions
  3. Chapter .ts manifests with section structure
  4. Paper .ts manifest (new or updated)

Tag all generated blocks with:

tags: ["imported", "source:<document-id>"]

Add meta.source referencing the upload:

meta: {
  source: "library/<document-id>",
  originalSection: "3.2",
  importedAt: "2026-03-25T..."
}

WHO guidelines follow predictable patterns:

Label conventions for guidelines

Element Label pattern Example
Recommendation def:who-<guideline>-rec-<N> def:who-anc-rec-1
Evidence summary prose:who-<guideline>-evidence-<N> —
Remark rem:who-<guideline>-remark-<N> rem:who-anc-remark-1
Good practice prop:who-<guideline>-gps-<N> prop:who-anc-gps-1
Research priority conj:who-<guideline>-research-<N> conj:who-anc-research-1

Cross-referencing WHO recommendations

WHO recommendations often reference each other and external evidence. Map these to uses[] in content objects:

export default definition({
  label: "def:who-anc-rec-3",
  title: "Recommendation 3: Daily iron supplementation",
  uses: ["def:who-anc-rec-1"],  // references Rec 1
  tags: ["imported", "source:who-anc-2016", "L1", "normative"],
  meta: {
    source: "library/who-anc-2016",
    strength: "strong",
    quality: "moderate",
    gradeLevel: "⊕⊕⊕◯",
  }
});

Resuming Partial Processing

The intake.json pipeline stage tracks where processing stopped. To resume:

  1. Read intake.json → check pipeline.stage
  2. Skip completed stages
  3. Continue from the current stage
  4. Update intake.json after each stage

This allows multi-session processing of large documents.

Checklist

Before marking intake complete:

  • Raw files committed to library/<document-id>/
  • intake.json has complete metadata
  • extracted-text.md reviewed for OCR errors
  • extracted-blocks.json reviewed and confirmed by user
  • All content objects generated with correct builders
  • Blocks tagged with ["imported", "source:<document-id>"]
  • Chapter/section structure matches document
  • Cross-references mapped to uses[]
  • intake.json stage set to generated
  • Content validation passes (content_validate)
