    Bridges from the scattered cell statistics onto the single home #

    Bean qou-cdup. QOU.MathlibExt.YoungDiagramCells is the one home for content / arm / leg / hook; this file connects the pre-existing copies to it, so a lemma proved against one is usable against any other.

    Why bridges rather than a migration #

    Deleting each local definition and rewriting its call sites would touch proofs in six modules at once. These lemmas are purely additive — no existing file changes — and they are what a later migration would rewrite along. They also test a claim I had so far only asserted, in a bean and two commit messages, namely that every copy is definitionally equal so every bridge is rfl.

    What the test found #

    Thirteen bridges land: twelve by rfl, one conditional. Two copies cannot be bridged at all. Broken down, because a single number here would hide the two different things being counted — content copies, and arm/leg/hook copies:

    reachable rfl
    content copies (8 in the tree) 6 6
    arm / leg / hook copies (2 sets) 2 6 lemmas
    hookLength (ℕ-valued) 1 no — needs c ∈ μ

    The blanket claim I had been repeating — "eight copies, each a rfl bridge" — was wrong in both directions:

    • Two copies are unreachable. QOU.BraidsAndKnots.cellContent (mass-theory/y-lambda-recipe-from-partition.lean) and QOU.BraidKnot.cellContent (mass-theory/jucys-murphy-central-elements-qou.lean) live in standalone content-block siblings, not library modules, so nothing can import them. The second is additionally the clash partner from the cdup record — it shares a fully-qualified name with a library declaration — so it is unbridgeable by construction: importing both is the very error the bridge would have to survive.
    • hookLength is not rfl. TwoFiltrationBridge.hookLength is valued in ℕ with truncated subtraction, so it agrees with the ℤ-valued hook only on cells of the diagram — off-diagram the ℕ version saturates at 0 while the ℤ version goes negative. It is a real lemma with a hypothesis, and recording it as "a rfl bridge" would have been wrong.

    So the honest count for the migration is: six free, one conditional, two requiring the sibling to be promoted to a library module first.

    Superseded — read the 2026-08-24 section below before trusting the table above. Re-measured from the tree rather than from this record, there are ten reachable content copies, not eight; four were never listed anywhere, including one this record explicitly claimed does not exist. axialDistance is duplicated three times, and that is where the duplication stops being cosmetic.

    2026-08-24 — four more content copies, and the axialDistance pair #

    Re-measured from scratch rather than from the record above, and the record was wrong again — in the direction that matters, under-counting.

    There are ten content copies in the library tree, not six. Four were never listed anywhere:

    declaration file why it was missed
    QOU.SchurWeyl.cellContent SchurWeyl/HoefsmitRep.lean:115 a cdup note claimed this one "does not exist"
    QOU.QBeta.WenzlWeight.content QBeta/WenzlWeightVanishing.lean:91 never listed
    QOU.Hecke.content Hecke/Hoefsmit.lean:80 never listed
    QOU.HeckeAlgebra.JonesMarkovWenzl.cellContent HeckeAlgebra/JonesMarkovWenzl.lean:195 never listed; carries an unused Partition argument, so a signature-shaped search misses it

    All four are rfl. The last takes a partition it ignores (_lam), which is why it looks like a different function and is not.

    Importing all of them together is safe. These six modules had never been co-imported; doing so here is itself the test that no two of the ten share a fully-qualified name. They do not — this file compiles.

    The axialDistance pair — the reason this stopped being cosmetic #

    content being duplicated costs duplicated effort. axialDistance being duplicated costs a silent rw failure, which is a different kind of bug:

    QOU.SchurWeyl.axialDistance and QOU.BraidKnot.TableauContent.axialDistance are rfl-equal but are different constants. Inside namespace QOU.SchurWeyl a bare axialDistance resolves to the first even under open QOU.BraidKnot.TableauContent — the enclosing namespace wins over the open. So a rw with a lemma stated in the other does not fire, and the error prints the two sides identically (axialDistance c (a, ν.rowLen a) both times), differing only in a fully-qualified name buried in the pattern line.

    Live instances already on opposite sides of that line: MarkovAssembly.markov_of_corner_identity uses the first, SeminormalNodeForm.axialDistance_corner_addable the second; QOU.SchurWeyl.axialDistance_eq_tableauContent in SchurWeyl/WenzlMarkovCorner.lean is the ad-hoc bridge written to compose them. That lemma stays where it is — callers depend on it — but it is now an instance of a general pattern rather than a one-off.

    The third axialDistance is in scope after all #

    QOU.Hecke.axialDistance was set aside as "tableau-indexed, a different signature, probably not part of this drain". Checked rather than assumed, and that is wrong on the part that matters: it is a different signature, but it is built on a fourth undocumented copy of content (QOU.Hecke.content, above), and it bridges — conditionally, one lemma per branch of its dite. Being differently-shaped kept it out of the duplication count while leaving it squarely inside the duplication.

    The tableau-indexed third copy #

    QOU.Hecke.axialDistance reads two cells out of a standard tableau and takes their content difference, with a dite guarding k+1 < n and a +1 index shift (its tableau coordinates are 0-based, its contents 1-based). It is not pointwise-equal to anything, so it gets one lemma per branch.

    source
    theorem QOU.MathlibExt.YoungDiagramCells.hecke_axialDistance_eq_of_lt {n : ℕ} {lam : Hecke.Partition n} (T : Hecke.StandardYoungTableau lam) (k : Fin n) (h : ↑k + 1 < n) :
    Hecke.axialDistance T k = axialDistance ((T.cells k).1 + 1, (T.cells k).2 + 1) ((T.cells ⟨↑k + 1, h⟩).1 + 1, (T.cells ⟨↑k + 1, h⟩).2 + 1)
    source
    theorem QOU.MathlibExt.YoungDiagramCells.hecke_axialDistance_eq_zero {n : ℕ} {lam : Hecke.Partition n} (T : Hecke.StandardYoungTableau lam) (k : Fin n) (h : ¬↑k + 1 < n) :
    Hecke.axialDistance T k = 0
    source
    theorem QOU.MathlibExt.YoungDiagramCells.hecke_axialDistance_eq_unshifted {n : ℕ} {lam : Hecke.Partition n} (T : Hecke.StandardYoungTableau lam) (k : Fin n) (h : ↑k + 1 < n) :
    Hecke.axialDistance T k = axialDistance (T.cells k) (T.cells ⟨↑k + 1, h⟩)

    The +1 shift is a translation of both cells, so it cancels: the Hecke axial distance is the canonical one on the unshifted tableau coordinates. This is what makes the shift a bookkeeping convention rather than a difference in the quantity being computed.
