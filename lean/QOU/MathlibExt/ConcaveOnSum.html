    QOU.MathlibExt.ConcaveOnSum — a Finset-indexed sum of concave functions is concave #

    Bean qou-mlgp Gap 3, second piece.

    The gap #

    Mathlib has the binary results — ConvexOn.add, ConcaveOn.add, StrictConcaveOn.add_concaveOn, ConcaveOn.add_strictConcaveOn — and it has Jensen (ConvexOn.map_sum_le, which is the different statement f (Σ wᵢ xᵢ) ≤ Σ wᵢ f xᵢ). It does not have the Finset-indexed sum of functions. Measured against the pinned revision (f897ebcf): grep -rn "ConvexOn.sum\|ConcaveOn.sum\|convexOn_sum\|concaveOn_sum" over all of Mathlib returns no hits.

    Why the corpus needs it #

    The hyperbolic volume of an ideal triangulation is a sum over its tetrahedra,

    `Vol(θ) = Σ_{i ∈ tetrahedra} ( Λ(αᵢ) + Λ(βᵢ) + Λ(γᵢ) )`,

    and Rivin's theorem is that this is strictly concave on the angle-structure polytope. QOU.Knot.RivinConcavitySimplex supplies the single-tetrahedron factor; the sum lemma is what turns one tetrahedron into a triangulation.

    The shape the strict version has to take, and why #

    StrictConcaveOn.sum_of_mem asks for one strictly concave summand and lets the rest be merely concave. That asymmetry is forced, not a convenience. Each per-tetrahedron volume, read as a function of the whole polytope, is constant in every other tetrahedron's angles — so it is concave but never strictly concave there. What rescues strictness is that a nonzero direction in the polytope must move some tetrahedron's angles, and that one summand is then strictly concave along it.

    A symmetric "all summands strictly concave" lemma would be true and useless here.

    Scope #

    Pure convexity API — no knots, no volume, no Λ. Written to be upstreamable unchanged, at the same generality as the binary lemmas it iterates.

    One strictly concave summand makes the whole sum strictly concave, provided the others are concave.

    This is the form the triangulation argument needs: see the module docstring for why asking all summands to be strictly concave would be the wrong hypothesis.
