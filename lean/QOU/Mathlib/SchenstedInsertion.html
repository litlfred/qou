    QOU.Mathlib.SchenstedInsertion — Schensted row insertion (RSK foundation, brick 1) #

    The Robinson–Schensted–Knuth correspondence — whose cardinality consequence ∑_{λ ⊢ n} #SYT(λ)² = n! is Identity-I axiom (i) (stated as RSKBurnsideHolds in QOU/Mathlib/RSKBurnsideTarget.lean) — is built on the row-insertion (bumping) operation. Pinned Mathlib has no Combinatorics.RSK (recon 2026-06-26), so this multi-session program formalises it brick by brick. Brick 1 (this file): the atomic row-insertion on a single row, modelled as a weakly-increasing List ℕ, with its two structural invariants proved sorry-free.

    rowInsert r x inserts x into a weakly-increasing row r by the Schensted rule: replace the leftmost entry strictly greater than x by x and return that bumped entry; if no such entry exists, append x (no bump). Returned as (newRow, bumped?).

    Proved here (sorry-free):

    • mem_rowInsert — every entry of the new row is an old entry or x;
    • rowInsert_length — the row length is unchanged (a bump) or grows by one (an append);
    • rowInsert_sorted — the new row stays weakly increasing (the key invariant that makes the insertion tableau well-formed).

    Roadmap for the remaining bricks (each a future PR): the bumping cascade across rows (insertion tableau P), the recording tableau Q, the pair (P, Q) as the RSK map, its inverse (reverse bumping), the resulting bijection Sym n ≃ Σ_λ SYT(λ)², and finally the cardinality count discharging RSKBurnsideHolds. Pure combinatorics on ℕ; nothing archimedean.

                  Brick 5 — bumping monotonicity (toward column-strictness) #

                  The column-strictness of the insertion tableau (columns strictly increasing — the invariant making P(w) a genuine semistandard tableau) rests on the bumping lemma. Its atomic seed is proved here: a rowInsert bump ejects an entry strictly greater than the inserted value. So the value cascading into the next row is always > x, which is what forces each new cell to sit strictly below a smaller entry. (The full cascade column-strictness is the next sub-brick.)

                  Bump-column monotonicity (the bumping-lemma heart) #

                  The insertion tableau is column-strict because bump columns weakly decrease down the rows: if x bumps y from an upper row, y re-inserts into the lower row at a column no further right. The proof rests on a general List.findIdx fact — if the predicate already holds at position c, the first witness is ≤ c — plus column-strictness of the input (upper[j] < lower[j]).

                  Column-strictness invariant #

                  StrictBelow upper lower — lower is no longer than upper and each of its entries strictly exceeds the one directly above (getD _ 0 reads in-range entries, dodging dependent-index proofs). ColStrict T — consecutive rows of the tableau satisfy StrictBelow, i.e. columns strictly increase downward. Two entry-level preservation lemmas (append a cell to the upper row; lower an upper entry) feed the cascade preservation.

                      Brick 6 — recording tableau Q (insertion-step bookkeeping) #

                      P(w) records WHICH values sit where; the recording tableau Q(w) records WHEN each cell was added — the step index of the insertion that created it. insertRec P Q x s performs one Schensted insertion of x into P while, in lockstep, writing the step index s into the matching new cell of Q: the single new cell of insert P x (Brick 3) gets value s in Q.
