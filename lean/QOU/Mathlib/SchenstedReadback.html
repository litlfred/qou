    QOU.Mathlib.SchenstedReadback — reading the row indices back off Q (RSK inverse, brick 5) #

    Brick 4 showed Q(w) is built by qAppending timestamp s at row rowIndices[s]. This file reads that back: qRowOf Q t locates the row of Q holding t, and the two lemmas below say qAppend puts the new timestamp exactly where brick 4 says and disturbs nothing else.

    • qRowOf — the row index of t in Q, as an Option.
    • qRowOf_qAppend_self — qRowOf (qAppend Q i s) s = some i, when s is fresh for Q.
    • qRowOf_qAppend_of_ne — for t ≠ s, appending s does not move t.

    The freshness hypothesis is not bookkeeping #

    qRowOf returns the first row containing t, so if t already occurs in Q the append cannot be located by looking for t — an earlier copy shadows it. Freshness is what makes the read-back a function of Q instead of a search with ties. In the RSK setting it is supplied by SchenstedRecording.insertWordRec_snd_content: the recording content is exactly range |w|, each timestamp occurring once, so every append is fresh at the moment it happens. That theorem was proved a while ago with no consumer; this is what it was for.

    Scope #

    The single-step read-back. Threading it along qAppendSteps to recover the whole index list — and thence rskPair injectivity, surjectivity, and RSKBurnsideHolds — is brick 6 and beyond. Nothing here claims them.
