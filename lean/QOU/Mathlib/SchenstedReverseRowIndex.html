    QOU.Mathlib.SchenstedReverseRowIndex — where reverse row insertion writes (RSK inverse, brick 12a) #

    Brick 1 defined rowUninsert and proved it inverts rowInsert on the bumping branch. Everything downstream that has to reason about columns — chiefly that the reverse cascade preserves ColStrict — needs more than that: it needs to know which index rowUninsert writes to, and that nothing to the right of that index was eligible.

    SchenstedInsertion has the forward counterpart (bump_findIdx_mono, getD_le_of_lt_findIdx, feeding strictBelow_bump_step and insert_colStrict). There is no reverse counterpart, so this file supplies one.

    rowUninsert_spec packages the whole story in a single existential: if reverse-inserting y into r displaces z, then there is an index k with

    • k < r.length and r.getD k 0 = z — z is the entry that was sitting at k;
    • (rowUninsert r y).1 = r.set k y — the row changed at k and nowhere else;
    • z < y — the replacement is strictly larger, which is what makes the column comparison move;
    • ∀ m, k < m → m < r.length → y ≤ r.getD m 0 — nothing to the right of k was eligible.

    That last clause is the one carrying the content. rowUninsert descends to the end of the row before deciding, so it takes the rightmost entry strictly below y; the column argument needs exactly that maximality, not merely "some entry was replaced".

    Three consequences follow, and the last is the one the whole reverse programme was waiting on:

    • le_index_of_lt — the write index dominates every eligible index (maximality, contrapositive);
    • reverse_bump_index_mono — reverse bump columns weakly increase going up, the mirror of bump_findIdx_mono;
    • strictBelow_reverse_bump_step — one adjacent-row step of column-strictness, the mirror of strictBelow_bump_step.

    Correction, recorded after the cascade was written. This file was built expecting strictBelow_reverse_bump_step to be what the cascade lifts. It is not. That lemma relates upper and lower when both rows are rowUninsert images, and in the cascade the row below the one being written is not always such an image — at the target row it is a dropLast, or the row is deleted. SchenstedCascadeColStrict therefore does its column cases directly and consumes only the index theory above: rowUninsert_spec, le_index_of_lt, reverse_bump_index_mono. The lemma stands as a correct mirror of the forward API; it is simply not the load-bearing one.

    I had expected the monotonicity to be the hard step. It is three lines: upper[kLow] < lower[kLow] makes kLow itself an eligible index in the upper row, and the write index dominates every eligible index. The pair-of-rows step is then four column cases, of which monotonicity kills the only bad one.

    Bump-column monotonicity, reversed #

    The forward cascade is column-strict because bump columns weakly decrease going down (bump_findIdx_mono). Reversed, they weakly increase going up: the reverse cascade removes a cell from a lower row and writes into the upper row at an index no further left.

    That is the one fact I expected to be the hard step of the reverse bumping lemma. It is not: it is the maximality clause of rowUninsert_spec read contrapositively, and needs no induction of its own. Both lemmas below are three lines.

    source
    theorem QOU.Mathlib.Schensted.le_index_of_lt {r : List ℕ} {y k j : ℕ} (hright : ∀ (m : ℕ), k < m → m < r.length → y ≤ r.getD m 0) (hj : j < r.length) (hjy : r.getD j 0 < y) :
    j ≤ k

    The write index dominates every eligible index. If any in-range entry of r is strictly below y, then rowUninsert writes at least that far right. Contrapositive of maximality.

    theorem QOU.Mathlib.Schensted.reverse_bump_index_mono {upper lower : List ℕ} {yLow kLow kUp : ℕ} (hsb : StrictBelow upper lower) (hkLow : kLow < lower.length) (hyLow : lower.getD kLow 0 = yLow) (hright : ∀ (m : ℕ), kUp < m → m < upper.length → yLow ≤ upper.getD m 0) :
    kLow ≤ kUp

    Reverse bump columns weakly increase going up — the mirror of bump_findIdx_mono.

    If the lower row gave up its entry at kLow, and the upper row sits strictly above it (StrictBelow upper lower), then reverse-inserting that entry into the upper row writes at an index kUp ≥ kLow.

    The proof is the whole reason column-strictness survives: upper[kLow] < lower[kLow] = yLow, so kLow is itself an eligible index in the upper row, and the write index dominates every eligible index.

    One adjacent-row step of column-strictness, reversed #

    With monotonicity in hand the pair-of-rows step goes through directly — the mirror of strictBelow_bump_step.

    source
    theorem QOU.Mathlib.Schensted.strictBelow_reverse_bump_step {upper lower : List ℕ} {yBelow yLow yUp : ℕ} (hsb : StrictBelow upper lower) (hlow : (rowUninsert lower yBelow).2 = some yLow) (hup : (rowUninsert upper yLow).2 = some yUp) :
    StrictBelow (rowUninsert upper yLow).1 (rowUninsert lower yBelow).1

    A reverse bump keeps the two rows column-strict.

    lower gives up its entry yLow (writing yBelow in its place), yLow is reverse-inserted into upper (writing yLow in place of yUp), and the pair stays StrictBelow.

    Four column cases, and monotonicity kills the only bad one:

    • j = kUp = kLow — the upper row now reads yLow, the lower row now reads yBelow, and yLow < yBelow because a reverse insertion always writes something strictly larger.
    • j = kUp > kLow — the lower row is unchanged at j, and lt_of_index_lt on the lower row's maximality gives yLow < lower[j].
    • j = kLow < kUp — the upper row is unchanged at j, and upper[kLow] < lower[kLow] = yLow < yBelow.
    • neither — both rows unchanged at j.

    j = kUp < kLow is the case that would break it, and reverse_bump_index_mono excludes it.

    The rightmost choice, machine-checked #

    rowUninsert [1,2,4] 3 has two eligible entries (1 and 2 are both < 3). It must take the right-hand one. If it took the leftmost the result would be ([3,2,4], some 1), which is not even weakly increasing — so this witness also shows why rowUninsert_sorted needs the rightmost convention rather than merely some eligible entry.
