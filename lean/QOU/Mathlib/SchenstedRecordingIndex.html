    QOU.Mathlib.SchenstedRecordingIndex — the recording tableau is the row-index record #

    Brick 4 of epic qou-nrex (RSK inverse).

    Brick 3 showed the word is recoverable from the insertion tableau plus the list of rows each step appended to (rowIndices). That list looked like extra data. It is not: it is exactly what the recording tableau Q(w) holds. This file proves the identification, at both levels.

    • qAppend Q i s — write timestamp s at the end of Q's row i. This is precisely the bookkeeping insertRec performs on its Q argument, extracted as a function of the row index.
    • insertRec_snd_eq_qAppend — one step: (insertRec P Q x s).2 = qAppend Q (newRowIndex P x) s. So the row insertRec writes into is the row insert appends to — the same newRowIndex brick 2 defined, with no separate notion of "where Q grew".
    • qAppendSteps / insertWordRecAux_snd_eq_qAppendSteps — the whole fold: Q(w) is qAppended along rowIndices, timestamps counting up from the start index.
    • insertWordRec_snd_eq_qAppendSteps — at the empty tableau, the form the inverse consumes.

    What this closes #

    Brick 3's word_eq_of_insertWord_eq needed equal insertion tableaux and equal index records. The index record is now a function of Q rather than side information, so the pair (P, Q) alone determines the word — the injectivity half of the RSK bijection, modulo reading rowIndices back off Q (which is where the timestamps' Nodup/range content from SchenstedRecording enters).

    Scope #

    The forward identification only: Q is built by these appends. Recovering rowIndices from a given Q — inverting qAppendSteps — is the next step, and rskPair bijectivity and RSKBurnsideHolds are past it. Nothing here claims them.
