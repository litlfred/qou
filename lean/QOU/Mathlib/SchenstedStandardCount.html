    QOU.Mathlib.SchenstedStandardCount — the counting bridge from column-strictness (brick 23) #

    Brick 22 showed the shape an addable sequence builds is the count shape: row i holds exactly the steps that landed in row i. So IsAddable at a step reduces to a comparison of counts, and what the recording tableau has to supply is exactly that comparison.

    This file proves it, from column-strictness alone:

    countLt_above — if an entry k sits at column c of row r + 1, then row r holds strictly more entries below k.

    Read through brick 22, that inequality is the addability condition: the row above has more cells placed before time k than the row the new cell goes into, which is what makes the new cell addable.

    What it does not need #

    No truncation of the tableau. An earlier plan restricted Q to its entries below s, proved ColStrict survived the filter and that the emptied rows formed a suffix — several hundred lines. Counting per row replaces all of it, because brick 22 already phrased the shape as a count.

    It also needs no notion of "standard" beyond what is written in the hypotheses: rows strictly increasing and columns strictly increasing. There is no standardness predicate here, and none is introduced — the third time on this arc that checking what the argument consumes turned out to shrink the machinery.

    Scope #

    The counting fact. Producing the position sequence from a recording tableau — reading rows off Q in timestamp order and assembling AddableAlong — is the next brick of epic qou-nrex. Nothing here claims it, nothing here claims rskPair is bijective, and RSKBurnsideHolds for general n stays open (proved for n ≤ 12 by an unrelated route, PartitionsOfBridge.rskBurnsideHolds_le12, with no RSK correspondence in it).

    Pure combinatorics on ℕ; nothing archimedean.

    Scope note superseded (2026-08-23). The scope paragraph above records the state of the arc when this brick landed. RSKBurnsideHolds is now proved for every n (QOU.Mathlib.rskBurnsideHolds, brick 42), and SnIsotypicSpechtSplit is inhabited, so any statement here that they "remain open" or hold "only for n ≤ 12" describes history rather than the corpus. The per-brick scope is otherwise unchanged and still accurate.

      The bridge fact. If an entry sits at column c of row r + 1, then row r holds strictly more entries below it.

      Column-strictness supplies both halves: the entry directly above is smaller, and — via the length half of StrictBelow — that cell exists at all. Row r therefore has its first c + 1 entries below the threshold, against exactly c in row r + 1.

      The membership form #

      countLt_above is indexed by the column, but qRowOf — the corpus's timestamp locator — returns only the row. Nothing in bricks 4-6 records the column, so the assembly cannot supply one.

      It does not have to: in a strictly increasing row the column of an entry is its countLt, so the column is recoverable rather than needing to be carried. getD_countLt below is that recovery, and countLt_above_mem is countLt_above restated to take membership instead of a column index — the form the assembly can actually reach.

      qRowOf correctness #

      qRowOf is total and exact, given distinct entries #

      Brick 24 gave one direction: the located row contains the timestamp. The counting step needs the converse — if t sits in row i, qRowOf must return i — and that is where entries being distinct across rows finally matters. qRowOf returns the first row containing t, so without distinctness a repeated entry would be located in the wrong row.

      Totality is separate and needs no distinctness. It matters because qRowOf returns an Option: a counting argument that reads it with .getD 0 would silently score every absent timestamp as row 0.

      The count equality #

      The step the whole Q-side reduces to. Brick 22 phrased the shape an addable sequence builds as a count over the position list; countLt counts over the rows of Q. These are the same number, and this is where that is proved.

      The two sides genuinely count different things — timestamps on the left, entries on the right — so the argument is a bijection, not a rewrite. Both filtered lists are duplicate-free and have the same members, which is enough.

        The chain, closed #

        Every link is now in place, so it is worth stating the composite rather than leaving a reader to assemble it:

        Q standard ──26──▶ AddableAlong ──20──▶ ShapeCornersAlong ──18──▶ insertWord ∘ uninsertSteps = id

        The only hypothesis tying P to Q is that they have the same shape, which is what "a pair of tableaux of the same shape" means.
