    Which UIC functional is Lean-provable: the gate needs data the block's formula discards #

    Owner ruling, 2026-09-12, verbatim: "resolve functionals ... what lean provable".

    prop:unified-iterative-correction displays

    B_λ = m_e · H_q(λ) · u_λ · ( ln|tr M_λ| − ln d_λ ),   summed "strictly over all λ",

    while computations/hecke_core_legacy.py::unified_iterative_correction sums the same shape over only those λ whose signed final trace satisfies tr M_λ(atom) ≤ 0 (Pass 2, lines 2176-2188). The two differ by a measured factor 3.4-4.6 (hecke_core_legacy.py:2148-2153).

    This file is the resolution's mathematical content. It is not a claim about which functional the physics wants. It is the structural fact that decides what can be stated:

    • the block's displayed summand reads the trace only through ln|tr|, hence is even in the trace — uicAll_sign_blind;
    • the producer's gate reads sign(tr), which evenness has destroyed, so the gated total is not a function of the data the block displays — gate_not_a_function_of_displayed_data;
    • therefore the block's formula, as written, cannot express the producer's functional, whatever one decides about the physics. Something has to move.

    Two further results bear on which:

    • uicGated_cs_eq — under genuine complementary slackness for a constraint ⟨Φ, π_λ⟩ ≥ 0, "tight" means tr = 0, and then the gated functional collapses to (Σ_{selected} c_λ) · f 0: it carries no trace information at all and cannot distinguish two atoms. So complementary slackness does not justify the coded gate tr ≤ 0; it justifies nothing that varies with the nucleus.
    • uicGated_nonpos — a non-negative scale against a non-positive log-ratio forces B ≤ 0 on the gated set, for any index set. This is the Lean form of computations/probes/uic_sign_forced_by_gate_probe.py.

    Nothing here is conditional on a class, and nothing here assumes the gate. The degeneracy that removes the gate's stated justification is proved elsewhere and sorry-free: QOU.ParticleInteractions.y_0_eq_zero_of_radical (operator_selection_lp.lean:390).

    Base ring #

    Everything except the two explicit witnesses is generic [CommRing R]; the witnesses are over ℚ because they need an order and a decidable ≤. No ℝ appears — the archimedean instantiation (f = fun x => Real.log |x| - Real.log d is even) lives in QOU.MassTheory.UICLogSummandEven, per AGENTS.md §7c.

          The discriminator, with an explicit witness #

          The witness is over ℚ with a single block. ℚ because the gate needs a decidable ≤; one block because one is enough — the failure is not a matter of size.

          source
          theorem QOU.MassTheory.UICFunctionalSelection.gate_not_a_function_of_displayed_data :
          ∃ (c : Fin 1 → ℚ) (f : ℚ → ℚ) (τ : Fin 1 → ℚ) (τ' : Fin 1 → ℚ), (∀ (x : ℚ), f (-x) = f x) ∧ (∀ (i : Fin 1), f (τ i) = f (τ' i)) ∧ uicAll c f τ = uicAll c f τ' ∧ (uicGated c f τ fun (i : Fin 1) => τ i ≤ 0) ≠ uicGated c f τ' fun (i : Fin 1) => τ' i ≤ 0

          The producer's gate is not a function of the data the block's formula displays.

          Two trace vectors that agree on every value the displayed formula reads — f (τ i) for all i — give different gated totals. So there is no way to write the producer's functional in the block's own variables: the gate needs the sign, and ln|tr| has already thrown it away.

          This is the resolution's load-bearing theorem. It says the mismatch is structural, not editorial: the block's text is not a loose paraphrase of the producer, it is a formula that cannot denote what the producer computes.
