## The bean this came from was stale

`qou-6ixs` names four raw-float64-dirty witnesses (qns-backscatter,
gswz_epsm x2, qbeta-g3-aomega). **None is dirty now** — other sessions
drained 12 files / +2,333 fields since baseline, and the audit reports
`NEW dirty witnesses: 0`. `qns-backscatter` was never a drain target at
all: it sits under the **declared** float64-integrator carve-out (19
fields, `precision_tier='float64-integrator'`), which is the correct
disposition rather than something to fix.

The one live red on the raw-float64 ratchet is a different witness that
`qou-6ixs` predates.

## What the regression actually is

`computations/rho-k-co-casimir-extended.witness.json` REGRESSED 3 -> 4.
All four fields are `compute_wall_sec` — wall-clock telemetry, not
physics, and incapable of propagating into a derivation:

```
.data.per_atom[2].compute_wall_sec = 0.34
.data.per_atom[3].compute_wall_sec = 9.28
.data.per_atom[4].compute_wall_sec = 9.45
.data.per_atom[5].compute_wall_sec = 2533.2
```

**The producer is already correct.** `rho_k_co_casimir_extended.py:354`
emits `f"{t1 - t0:.2f}"` — a string — fixed in `29b209ce93` ("float64:
four timing fields serialised as strings"). The witness simply predates
it: recorded `scriptHash` `6b46797533d4` vs producer `aa4e42c6f2da`.

The witness is built by an **incremental accumulator**
(`_save_incremental`, `add_data("per_atom", results_so_far)`), so it
carries entries from three producer generations: `[0],[1]` predate the
field entirely, `[2]-[5]` hold the old float form, none carry the current
string form. The "regression" is a fourth stale entry surfacing, not new
dirt.

## Why regenerating is worth it anyway

Not cosmetic. The witness also predates `3da4539d45` ("serialize chi at
the precision it actually carries — 148 fields"), so it is currently
carrying under-precision values. Regeneration propagates two real fixes.

## Why it is NOT done — compute, and an unexplained slowdown

Attempted 2026-08-15, `python3 -u ... | tee`. Killed after ~9 min.

| atom | n | recorded wall | this run |
|---|---|---|---|
| deuteron | 6 | 0.34 s | completed |
| tritium | 9 | **9.28 s** | **>8 min, still running** |
| helium-4 | 12 | **2533 s** | never reached |

Tritium ran ~50x over its recorded time, with helium-4 (itself 42 min on
the recorded box) still ahead. Naive extrapolation puts a full run in the
tens of hours.

**Two hypotheses checked and rejected — do not repeat them:**

1. *Precision was raised.* NO. `mp.mp.dps = 60` at module level and the
   worker path are **byte-identical** between the witness's recorded
   commit `c37cbd50ef` and HEAD.
2. *Machine contention.* PARTIAL ONLY. Load average 9.34 on 4 CPUs
   (~2.3x oversubscribed, no cgroup quota), workers pinned at ~48% CPU
   each. That accounts for roughly 2x, not 50x.

The remaining gap is **unexplained**. I am not offering a third guess.

## Trap for whoever picks this up

**Do NOT interrupt a partial run and commit the result.**
`_save_incremental` writes only `results_so_far`, so an interrupted run
produces a witness with ONLY the completed atoms — it would silently
DELETE the helium-4 entry. On abort, `git checkout --` the witness. That
is what was done here; the committed witness is intact with all six
atoms and the tree is clean.

## Next step

Run on an uncontended box. Use tritium as a **canary**: if it does not
land near 9.28 s there, the ~50x slowdown is real and is itself the
finding — a producer that silently got orders of magnitude more expensive
matters more than four telemetry floats.

Do not drain by hand-editing the four values, and do not baseline them.
