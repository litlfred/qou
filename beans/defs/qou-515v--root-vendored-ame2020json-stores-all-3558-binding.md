## Measured 2026-08-16 (found while draining qou-5sg8's last follow-up)

    qou-mass/src/qou_mass/data/ame2020.json
      entries                                  3558
      binding_energy_total_keV typed as float  3558   (ALL of them)
      with visible float64 artifact tails       640

Examples, where the intended value is obvious:

    Z=3 A=6    31993.987199999996    should be 31993.9872
    Z=1 A=6     5769.8369999999995
    Z=2 A=6    29271.119400000003
    Z=5 A=11   76205.05529999999

### Why this is the ROOT, not another instance

`codata_constants._ame_binding_mev` does `mp.mpf(str(entry[...])) / 1000` inside
`workdps(>= 50)`. That lift is CORRECT -- it faithfully carries what the file
says. The noise is already in the file, so it is *below* every AME constant in
the registry:

    ame2020.json (float64)  ->  _ame_binding_mev  ->  AME_B_*_MEV_VALIDATION
                                                  ->  ame_binding_mev(Z, A)
                                                  ->  every consumer

So `AME_B_LI6_MEV_VALIDATION` is `31.993987199999996`, and no amount of mpf
discipline downstream recovers `31.9939872`. Every NO-FLOAT64 fix above this
layer -- including the ones I just landed -- is correct and still cannot produce
a clean 6Li.

### Why I did not fix it in the same pass

Correcting it is a DATA REGENERATION from the published AME2020 source (the keV
values are exact decimals there), not an edit. Two hard constraints:

  1. NO HAND TYPED VALUES (owner, 2026-08-16). Typing 3558 corrected numbers is
     precisely the failure mode the rest of that session removed. The fix has to
     re-derive the file from the authoritative source, ideally emitting the keV
     field as a STRING so mpf lifts it exactly.
  2. `qou-mass/src/qou_mass/_internal/` is generated by
     scripts/sync-qou-mass-vendor.py. Whether `data/` is also generated needs
     checking FIRST -- if it is, the fix belongs at the generator and editing
     the JSON would be overwritten.

### Next steps

  1. Determine whether data/ame2020.json is generated or vendored-by-hand.
  2. Find the authoritative AME2020 mass-evaluation source already in the repo
     (or its provenance note) -- do not re-download blind.
  3. Regenerate with keV as decimal STRINGS, not floats.
  4. Re-run the registry consumers; expect small value shifts (~1e-15 relative,
     i.e. the float64 noise being removed) -- these are corrections, not
     regressions, and should be reported as such.

### Scope note

Scope-(a): this is a statement about the current vendored file, measured. It is
not a claim that AME2020 itself is wrong -- the published data is exact; the
float64 damage was introduced when this JSON was produced.
