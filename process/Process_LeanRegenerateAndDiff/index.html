nameIs the generated Lean in sync with its generators?
summaryCheck that the Lean text a script in this repository writes is still exactly what that script writes.
descriptionCheck that the Lean text a script in this repository writes is still exactly what that script writes. Two files carry such text: every knot block of QOU/Knot/GeneratedGluing.lean (from scripts/gen-gluing-lean.py) and the depth-3 corner column BokutShiaoCornerDepth3 in UGB/GrobnerShirshov/HeckeCompletion.lean (from scripts/gen-hecke-corner-column.py 3). WHY IT IS STRICT. These are proofs. If a generator and its output part company, a Lean file that compiles is carrying certificates nothing in the repository produces, and the next regeneration silently changes a proof. The check is cheap (about nine seconds) and writes nothing, so strictness costs nothing. THREE OUTCOMES, NOT TWO. A generator that cannot run, most often because SnapPy is not installed, is UNKNOWN and never reported as in sync. That is the parity rule the witness-parity Tool already follows. WHAT IS NOT CHECKED, AND WHY. The depth-2 column BokutShiaoCorner (section 4ad) was written by hand first; the generator was checked against it by re-deriving the same words and rules, not the same text. Measured 2026-10-05, the two differ on 964 lines while proving the same thing, so a textual diff there would report drift that is not drift. The module header of GeneratedGluing.lean and its closing end line are hand-written too, and are excluded from the comparison for the same reason. DRIFT IS A DECISION, NOT A FIX. When the regenerated text differs, either the generator changed (and the Lean should be regenerated) or the Lean was edited by hand (and the generator should learn the edit, or the edit should go). Which one is right is a judgement about a proof, so it goes to the author; the agent does not overwrite either side.
