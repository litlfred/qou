descriptionRun qou's compute-QA gates over computations/ and its witnesses, and publish one verdict per gate to the qa-reports branch. WHY ONE PROCESS. The gates used to live as inline steps in four workflow files, so nothing named them as a set, and the order an agent ran them in locally was whatever it remembered. They are now one table (scripts/compute-qa.py) and this one diagram; the workflows call the table, and each step carries a # bpmn-node: back-reference here. THE COMMANDS DID NOT CHANGE. Each gate runs the exact command the workflow step ran, with the same exit-code handling: a strict gate fails on a non-zero exit, a warn or advisory gate never fails the run and its output is the report; when it exits non-zero its verdict is WARN rather than PASS, so a finding is not recorded as green. Measured on main before the move and after it, every gate's exit codes and output are identical. QA IS AGENT-OWNED; CI IS A BACKUP. These workflows are dispatch-only (owner directive 2026-06-30, Actions billing), and several have never run. So the normal way through this process is an agent running python3 scripts/compute-qa.py before it commits, not CI. The lane says who runs a gate, not where. THREE OUTCOMES. A gate whose script cannot start (a missing module or binary) is UNKNOWN and never a pass. A failing self-test fails its gate whatever the gate's mode, because a detector that has stopped matching its known positive reports everything clean. VERDICTS ARE NOT COMMITTED. Each gate writes test/results/compute-qa/<gate>.json, which is gitignored and is the layout bun run qa:publish reads.
