# `braid-registry/` — retired 2026-08-25

269 JSON records, retired rather than regenerated. Three independent reasons,
each sufficient:

1. **Convention C.** 268 of the 269 carry `"z_markov": 0.4993200830735895`.
   Convention C was excised by owner ruling (2026-08-09, reaffirmed 2026-08-15
   R1); the canonical D value is `z = q³/(q²+1) = 0.6126880371464652…`.
2. **Neither pin.** All 269 record `"q": 1.11` — a rounded value that is neither
   the muon anchor (1.10997859555733471…) nor the canonical proton pin
   (1.1099785827513808…). Note this also means the recorded `z_markov` is not
   even C's value *at a real pin*: `z_C` at the proton pin is
   `0.49932033418369445`, against the `0.4993200830735895` here.
3. **Dead producer.** Generated by `_deprecated/braid-registry.py`, which is
   already retired. There is no live engine to regenerate them from under D.

**Nothing read them.** Verified before the move: no code path anywhere outside
`_deprecated/` opens this directory. The two files that mention "braid-registry"
(`hecke_core_legacy.py`, `ordering_cache.py`) do so only in prose — a docstring
naming the retired *script* as a historical ground-state seed and as a tier-3
fallback respectively, not a read of these records.

**This move changes no detector count**, and that is the point of recording it.
`scripts/convention-c-producer-audit.py` walks `*.py` via AST under
`computations`, `qou-mass` and `tools`; these are JSON, so they were never in
its range. They would have been found by the next person who greps the corpus
for a convention-C value and reasonably concluded axis B had reopened.

Found by the sibling working PR #5765 and confirmed independently here before
acting — including their "no runtime loader" claim, which a naive grep appears
to contradict and does not.
