Both reproduce under a recorded environment (`mpmath 1.3.0 / sympy 1.14.0 /
numpy 2.4.6 / scipy 1.17.1 / pyhecke_native 0.9.0`). A third crash,
`hadron_knot_table`, was **this container's missing `scipy`** and is not a
corpus defect — the CRASH count went 3 → 2 once it was installed. That
separation is only possible because the sweep now keeps stderr and stamps the
environment.

Neither of these witnesses can be regenerated by #5500 until its producer is
fixed. They are a hard blocker on that tranche, not staleness.

## 1. `derivation_chain_validator.py:254` — crashes ONLY when it finds something

```python
if rel > target_tolerance:
    structural_issues.append(
        f"c_q algebra re-eval at q_0={Q_0} gives {recomputed} "
        f"vs target {target_value} (rel_diff {rel:.2e}, "
        f"target_tolerance {target_tolerance:.2e})"
    )
```

`TypeError: unsupported format string passed to mpf.__format__` — `rel` is an
`mpf`, and `mpf.__format__` does not accept `.2e`.

**Read the guard.** That f-string is inside `if rel > target_tolerance`. It is
the *failure-reporting* branch. So this validator runs cleanly for as long as
the derivation chain agrees, and dies the moment it detects a discrepancy —
the crash is not incidental to the finding, it *is* the finding, thrown away.

Two consequences, and the second is the one that matters:

- The validator has been unable to report a structural issue for however long
  this has been true.
- **There is currently an undetected discrepancy in the c_q derivation chain.**
  The crash is proof the branch was entered. Fixing the formatting will surface
  a real number that nobody has seen — expect a finding, not a clean run.

Fix: `mp.nstr(rel, 3)` or `float(rel):.2e` **for display only** (per AGENTS.md,
`float()` is permitted inside an f-string and nowhere else). Then run it and
read what it says.

## 2. `habiro_interpolate_cross_validator.py:102` — eval binding mismatch

```python
return mp.mpf(eval(s, {"__builtins__": {}}, {"check_q": u_value, "mp": mp}))
```

`NameError: name 'u' is not defined` — the stored expression references `u`,
the locals dict binds it as `check_q`. A rename on one side only.

Fix: bind both names, or normalise the stored expressions. Whichever, check
which name the *stored data* uses rather than assuming.

**Secondary, unverified — flagging, not claiming.** `mp.mpf(eval(...))` wraps
the result *after* evaluation, so if any sub-expression evaluates in float the
`mpf` conversion cannot recover the lost digits. Whether that happens depends
on `u_value`'s type and the expression text, which I have not checked. Worth
looking at while the file is open, given the NO-FLOAT64 discipline; do not
record it as a defect without measuring it.
