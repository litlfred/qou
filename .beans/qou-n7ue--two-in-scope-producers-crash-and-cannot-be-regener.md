## 1. `derivation_chain_validator.py:254` — crashes ONLY when it finds something

```python
if rel > target_tolerance:
    structural_issues.append(
        f"c_q algebra re-eval at q_0={Q_0} gives {recomputed} "
        f"vs target {target_value} (rel_diff {rel:.2e}, "
        f"target_tolerance {target_tolerance:.2e})"

```

`TypeError: unsupported format string passed to mpf.__format__` — `rel` is an
`mpf`, and `mpf.__format__` does not accept `.2e`.

**Read the guard.** That f-string is inside `if rel > target_tolerance`. It is
the *failure-reporting* branch. So this validator runs cleanly for as long as
the derivation chain agrees, and dies the moment it detects a discrepancy —
the crash is not incidental to the finding, it *is* the finding, thrown away.

Two consequences, and the second is the one that matters:

- The validator has been unable to report a structural issue for however long
  this has been true.
- **There is currently an undetected discrepancy in the c_q derivation chain.**
  The crash is proof the branch was entered. Fixing the formatting will surface
  a real number that nobody has seen — expect a finding, not a clean run.

Fix: `mp.nstr(rel, 3)` or `float(rel):.2e` **for display only** (per AGENTS.md,
`float()` is permitted inside an f-string and nowhere else). Then run it and
read what it says.

## 3. `hadron_knot_table.py` → `hecke_core_legacy.py:1010` — float64 matrices meet mpf vectors

The Hecke Y-matrices are built in **float64** and then multiplied against an
**object-dtype** (`mpmath.mpf`) vector, which scipy refuses to upcast. Both
build paths do it:

```python
use_sparse = dim >= sparse_threshold
if use_sparse:
    from scipy.sparse import csr_matrix    # -> float64 CSR
...
    M = [[0.0] * dim for _ in range(dim)]  # dense path: float64 zeros
```

Read against the NO-FLOAT64 discipline, **scipy is doing the right thing**. The
`TypeError` is a refusal to silently mix a float64 operator with an
exact-carried vector; had it upcast, the producer would have run and quietly
resolved the mpf side to float64 — a precision violation that emits a witness
instead of an error. The crash is the guardrail working.

So the fix is **not** to cast the vector to float64 to make it run. It is to
build the matrices over the same exact ring the vector is carried in, or to
keep an exact non-scipy path for this case. Casting to clear the error would
convert a loud failure into a silent wrong number, which is the trade this
repo's precision rules exist to refuse.

Caveat worth checking before anyone starts: the module is named
`hecke_core_legacy.py`. Confirm whether `hadron_knot_table` should be on it at
all — the cheapest fix may be retargeting the consumer rather than repairing
the legacy path.

## `vhat_per_crossing_chain` FIXED — `1c0b2dbd0d`. CRASH -> exit 0, witness written.

numpy refused the run (`Cannot cast ufunc 'lstsq' input 1 from dtype('O') to
dtype('float64')`) because the chain's `(c, d)` are `mpf`. **numpy was right to
refuse** — satisfying LAPACK would have meant discarding the exact
coefficients.

`lstsq` was never needed. The routine's own docstring says the reduced element
lies in `span{σ, I}` by the Hecke quadratic, *"so the fit is exact"* — a
determined 2×2 solve dressed as least squares, paying float64 for the costume.
Replaced with the closed form in `mpf`. Note σ is **diagonal** here, so the
obvious `a = M01/s01` divides by zero; the code picks an independent row pair
and raises if σ is a multiple of the identity. The exactness the docstring
asserts is now **checked** (residual < 1e-30), not assumed.

### Three defects that surfaced only because it could run

1. `mpf.__format__` rejects `.6f` — **third instance of this class** this pass,
   after `derivation_chain_validator`. `float()` display-only.
2. `json` cannot encode `mpf`. Serialized via `_precision.fmt` at the **write
   boundary**, not at insert — `records` is also the computation store, and my
   first attempt serialized early and handed `max()`/`abs()` downstream a
   `str`. Witness raw-float64 fields: **0**.
3. **never-raises-dps ratchet went RED.** `mp.dps` is **15** after the
   transitive imports and **70** after `set_compute_dps()` — precision was
   inherited, not declared.

**I got (3) wrong first and the measurement corrected me.** I claimed the
60-digit witness strings were "padding a 15-digit value". They were not: before
and after agree to **50–51 significant digits**, so the compute was already
high-precision by some path. What the fix actually changes is that precision is
now *declared* before the imports that bind constants, moving the last ~9 of 60
digits. I have not established which constant moved and am not claiming it.

### SCOPE — this does NOT make the producer exact

σ comes from `_cached_seminormal` as **float64**, and `mpf(str(σ_ij))`
**launders rather than recovers**: 17 digits in, 17 digits of accuracy out,
however many are carried. The gate names `mpf(str(<f64>))` as a defect class
and lists 8 sites; this file is not among them, but I am not leaning on the
detector's silence — detector blindness is a documented pattern here and this
is the pattern in substance.

So: the arithmetic no longer *loses* precision downstream of σ, and σ's float64
origin is now the binding limit. The two routes agree to ~15 digits — the
float64 floor of the **other** route, which starts `a, b = 0.0, 1.0`. An exact
seminormal source is separate work.

Also corrected a stale docstring: the header said `z = 1/(q^½+q^−½)`
(convention C) over a value measuring `0.61268803714646525 = q³/(q²+1)` —
**convention D**. Right value, wrong name, the exact hazard AGENTS.md flags.

### `hadron_knot_table` — two defects, and a cost worth naming

1. `unified_iterative_correction` fed an `mpf`-carrying `M` to scipy's sparse
   kernels, which are float64-only. **scipy was right to refuse** — the only
   way to satisfy it is to discard the exact coefficients. numpy's `@` does
   support object dtype, so exact chains now route to the dense path.
2. `_crossing_in_partition` — **latent, exposed only by fixing (1)**:
   `np.asarray(csr_matrix)` does **not** densify; it returns a 0-d *object*
   array wrapping the matrix. So `c * sig_np` stayed object and the same
   `TypeError` fired one frame down. The `dim < 8` branch is worse — `sig[i][j]`
   is not valid indexing on a `csr_matrix` at all. Both unreachable while
   sparse-sigma states never took that path.

**Honest status: CRASH → unmeasured-at-600 s, not green.** It computes proton,
neutron and protium and proceeds, where it previously died in seconds. But an
exact chain gives up scipy's `O(dim·nnz)` kernel for dense `O(dim³)`, and that
is structural. Restoring the complexity for exact chains needs an mpmath-aware
sparse product — separate work. Float64 chains are untouched by construction.

I also cannot check the exact path against a prior value, because it never ran.
No agreement is claimed that was not measured.

### `parabolic_cylinder_channel_mixing_probe` — the one that was not a code defect

`R(nu) = √2·|Γ((1−nu)/2)/Γ(−nu/2)|` is an **absolute value**, so `R ≥ 0` for
every `nu`. 3He's `rho = −0.15171379` is **negative**, so `R(nu) = rho` has no
solution *at all* — not "none in (0,1)", not a bracketing or starting-point
problem. mpmath's own advice ("Try another starting point or tweak arguments")
is precisely the wrong instinct: no argument makes an absolute value negative.

The sign is **physical** — 3H and 3He are mirror nuclei with opposite odd-channel
parts (`+0.15173766` vs `−0.15171379`).

The probe now records 3He as unsolvable with that reason and continues. **And it
withholds `n_organized`:** that verdict compares within-N-class against
across-class spread, and dropping 3He leaves the N=1 class a **singleton**, so
within-class spread is identically 0 and the comparison is degenerate. A verdict
on the reduced sample would be a weaker claim wearing the stronger one's name.

**OPEN, and deliberately not decided by me:** whether the correct reading is to
invert `|rho|` and carry the sign separately. That is a question about what the
probe *claims*, not about how it runs, and it is the owner's call. Until it is
answered, this probe has no `n_organized` verdict.
