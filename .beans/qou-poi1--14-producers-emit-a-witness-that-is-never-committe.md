## The hole

`witness_raw_float64_audit.py` scans **committed** `*.witness.json`. A producer
whose witness is never committed therefore cannot be flagged by it, no matter
how dirty its output is — the ratchet's coverage is the tracked tree, not the
set of producers.

Measured on `main` 2026-08-26, over the 1554 producers that declare
`WitnessBuilder("<literal>")`:

    1554   declare a witness name
      14   whose <name>.witness.json is NOT tracked in git
       0   of those 14 are gitignored

The name mapping is exact and not a guess — `witness.py:1117`: *"Computation
name (becomes the filename: `<name>.witness.json`)"* — and it was confirmed
end-to-end by running one of the 14 and watching it write exactly that file.

Since none of the 14 is gitignored, none of them is uncommitted **by design**.
(`.gitignore` does deliberately exclude several large witnesses under "Large
computation witnesses (regenerated by running the script)" — those are a
legitimate, separate class, and none of the 14 is in it.)

## At least one of the 14 is genuinely dirty — verified by running it

`qbeta_c3_barodd_determined_solve_probe` (71.7 s) emits
`qbeta-c3-barodd-determined-solve.witness.json` carrying **9 raw float64
fields**, all in `.assertions[*].{computed,expected,tolerance}`. With that file
present, `witness_raw_float64_audit.py --strict` **exits 1** and reports 3 NEW
dirty fields against the baseline. It has presumably been emitting them for as
long as it has existed, and nothing could report it.

The producer's own output says so at the point of writing:

    raw-float64: 9 raw float64 field(s) would enter the witness ...
    Carry mpmath.mpf from the source and serialize with _precision.fmt

So the builder-side warning fires correctly. What is missing is the *durable*
signal: a warning on stdout of an uncommitted run reaches nobody.

**The other 13 are candidates, not confirmed dirty.** Deciding each needs its
producer run.

## 14 is a LOWER BOUND on one shape, not the size of the hole

This counts only `WitnessBuilder("<string-literal>")`. Not counted:

* **hand-rolled writers.** Producers that `write_text` a JSON witness without
  `WitnessBuilder` at all. Three were found incidentally in the `qou-aj91`
  no-witness batch, and **two of them have committed witnesses carrying
  `scriptFile: null`** (`qbeta-argu-phase-branch-selection`,
  `qbeta-meridian-holonomy-anchor-swing`) — the "bare producers" class
  AGENTS.md describes. Those are the inverse problem: committed, so the
  ratchet CAN see them, but with no provenance link back to the producer, so
  no provenance-keyed audit can.
* **stdout-only probes.** Seven of the same batch of eleven write nothing at
  all. Nothing to be dirty, but also nothing to audit — see `qou-aj91`.
* a name built dynamically rather than passed as a literal.

## What NOT to do

Do not commit the 14 witnesses to make them visible. For
`qbeta-c3-barodd-determined-solve` that is *forbidden* — the audit says it
directly: *"Do NOT add the file to the baseline to silence this"*, and
committing a witness with 9 raw float64 fields grows a ratchet that is
supposed to only drain. Fix at the producer first (`mpmath.mpf` end to end,
serialize with `_precision.fmt`), then the witness can be committed clean.

## Found by

Trying to execute the `qou-aj91` no-witness batch. The batch's plan was
"re-run and commit the witness first, to get a muon baseline"; this producer
was the only one of eleven able to do that, and the ratchet blocked it. That
is the ratchet working — the point of this bean is that it only worked because
someone happened to run the producer.

## "the name mapping is exact" reasoning was wrong

### The false positive, and why the earlier argument did not hold

`delta_lambda_value_witness.py` declares `WitnessBuilder("delta-lambda-value")`
but **writes `delta-lambda-witness.json`**, deliberately, with the reason in a
comment beside it (a consumer expects that filename and TOP-LEVEL keys). That
file **is** tracked. So it is committed, ratchet-visible, and never belonged in
this list.

The body above argues the count is sound because *"the name mapping is exact —
witness.py:1117: Computation name (becomes the filename: `<name>.witness.json`)"*.
That is the **default**, not a guarantee: a producer can hoist the payload and
write wherever it likes. I verified the default from a docstring and never
checked whether any producer overrides it. One does.

Re-checked all 14 for the override shape (`write_text(json…)` / `json.dump`):
**exactly one has it.** The other thirteen have `writes=0`, so their
`.witness.json` string literals are upstream *reads*, not output paths. So the
corrected count is **13**, and the detector needs an "and does not write its
own output path" clause.

### The worst one is not a serialization bug

`chi_sym_alt_closed_form` does not merely serialize floats — it **computes** in
float64. Its signature is literally

    def chi_sym_closed_form(crossings, q: float) -> float

so the substrate parameter is typed `float64`, and
`add_parameter("q", float(Q0))` downcasts it on the way in. Line 187 mixes the
two:

    return (q + 1.0 / q) / 2.0 + h * float(_avg_color_delta()) / 4.0

`float(_avg_color_delta())` is a downcast inside an arithmetic expression, which
AGENTS.md names as the defining case: *"`hf = float(G.h)` followed by arithmetic
against it is a computation, not a display, and is a defect."* Fixing this one is
a producer rewrite, not a `fmt` call.

### What this changes about the bean's claim

The claim was "14 invisible, 1 verified dirty, 13 candidates". Measured, it is
**13 invisible, 3 verified dirty (47 fields), 3 verified clean, 4 unclassified
by timeout, 3 blocked on missing upstreams** — and 2 of those 3 are blocked by
this very hole.

Still a **lower bound on one shape**: hand-rolled writers and stdout-only
probes remain uncounted.


## 2026-08-26 — the hole hides more than float64: a verifier that verified nothing

Went to fix the cheapest of the three dirty producers
(`sublemma_2_1_h12_he4_phase25`, 2 fields) and found the float64 was the least
of it.

**It was emitting `allPassed: true` having verified nothing.**

    n_partitions_processed = 0
    n_partitions_verified  = 0
    assertion "all_processed_lambda_path_a_eq_path_b_machine_eps"
        computed = 0   expected = 0   passed = true
    description: "Verified 0/0 λ ⊢ 12 … max rel residual 0.00e+00"

The assertion is `n_pass == n_total`, trivially true when both are zero — the
compute-side analogue of `theorem X : True := trivial`, which this repo bans
in Lean and had no equivalent guard against in Python. Both are zero whenever
the F1 `chi_q_at_q0` cache is absent, because every target then hits the
`lam not in chi_a` continue.

The contradiction was already printed and nothing acted on it:

    Path A loaded from F1 cache: 0 λ ⊢ 12
    Processing 8 / 77 λ ⊢ 12 (dim ≤ 80)
    Verified: 0/0

**This is the payoff of the measurement.** The vacuous green was invisible for
exactly the reason this bean exists: the witness is never committed, so nothing
downstream ever read it. The ratchet hole does not just hide dirty numbers — it
hides a verification producer reporting success on an empty set.

**Fixed** (commit `60386f4e4`): refuses before writing, naming the count, the
cause and the remedy, in the repo's own guard idiom. Verified: exits 1, writes
no witness.

**Residual, deliberately not fixed:** the guard catches the fully-vacuous case
only. A PARTIAL cache (3 of 8 targets) still reports "Verified 3/3" while 8
were targeted. Tightening that changes behaviour beyond the bug.

**The 2 float64 fields are NOT fixed, on purpose.** The producer computes in
float64 throughout — `path_b_chi_h12(lam, beta_full, float(Q0))` downcasts the
substrate parameter into the compute — so formatting
`.data.max_relative_residual` with `_precision.fmt` would make a
float64-derived number merely *look* precise. That is the cosmetic move the
discipline forbids. Same conclusion as `chi_sym_alt_closed_form`: **all three
dirty producers need real rewrites, not `fmt` calls.** There is no cheap one.

### Method note, from a near-miss of my own

A first gate run regenerated `witness-provenance-audit` and
`q0-anchor-consistency-audit` while an untracked witness from a **pre-guard**
run was still on disk. Both counted a file that no longer exists —
`total_scanned` +1, and it appeared *by name* in the anchor audit's list.
Committing them would have written a phantom witness into the audit record.
Reverted and re-run on a clean tree.

**Delete the artefact before regenerating the audits, not after.**

## Method note: three ways to get "is it still running?" wrong

This cost real confusion three times in one session, and twice I propagated the
wrong remedy.

    pgrep -f poi1c.py                      # WRONG - matches its own command line
    ps -eo args | grep -qF /tmp/poi1c.py   # ALSO WRONG - same defect, one level down
    pgrep -x -f "python3 -u /tmp/poi1c.py" # correct: -x requires an EXACT full match

The second was written INTO a check-in message as the fix for the first, and it
reported "still going" about a process that had already died. The general point
is the one this whole arc keeps re-learning: **a detector whose pattern can
match the detector is not a detector.** Safest of all is a PID file written at
launch and tested with `kill -0`, which cannot self-match by construction.
