## What

`grep -c` over `computations/` + `tools/`: **254** producers hardcode the MUON
constant `1.1099785955573347...` as an import fallback for `q_parameter`. **78**
of them carry a comment within two lines calling it the *"proton-anchor re-pin"*
— the comment names one pin, the number is the other.

## Why it bites

`q_parameter` lives in `computations/substrate/`, so a bare
`from q_parameter import q_at` does **not** resolve when the producer is run
standalone. The `try/except` swallows it and the producer computes at the
hardcoded muon value — while `q0_anchor_manifest.json` declares it proton.

Found by running `e_hartree_round24_molecular_reuse.py` directly: it emitted
`q0 = 1.1099785955573347` (muon) though the manifest resolves proton. Its
committed proton witness was reproducible **only** under the migration sweep,
which happened to put `substrate/` on `sys.path`. So this is a reproducibility
defect as well as a pin defect: the witness on disk cannot be regenerated by
running its own producer.

## Already done (this branch)

- `computations/q0_stamp.py` — the shared stamp helper for hand-written
  witnesses now **refuses to stamp** when the payload's recorded q₀ contradicts
  the manifest pin, so this class can no longer manufacture a false `Q0_OK`.
  It lands `Q0_ANCHOR_MISSING` + a `q0AnchorReason`, which is visible.
- `e_hartree_round24_molecular_reuse.py` — imports `_path_bridge`, and its
  fallback constant is now the proton pin. Verified: standalone run reproduces
  the committed numbers exactly and stamps `proton`.

## Next

Sweep the remaining 253. For each: does it import `_path_bridge` (or otherwise
put `substrate/` on the path)? If not, the fallback is live and its witness may
be muon-valued under a proton declaration. Prefer fixing the *path* over
editing the constant — a resolved `q_at()` cannot go stale, a hardcoded literal
can. Re-run and diff each witness; the guard means an unfixed one now shows up
as `Q0_ANCHOR_MISSING` rather than silently passing.
